# Backend operation matrix

Use the exported declarations in [contract.ts](contract.ts), [resources.ts](resources.ts) and [taskspaces-api.ts](taskspaces-api.ts) for exact call and result types. This matrix records the implemented domain, read, taskspace and lifecycle surface. The LocalBackend contract runner remains pending. Packed core/client consumers validate public resource declarations and runtime identity. See the [Phase 2 task record](../../../../docs/backend-separation/Kozane-Client-Backend-Separation-and-Web-Demo-Tasks.md) for Gate 3 acceptance evidence.

## Shared rules

Identifiers are strings. A supplied namespace identifies the board, and taskspace IDs must be visible there. Optional fields accept omission or undefined. Null is accepted only where the exported type includes it. No operation automatically replays a rejected mutation.

Reads do not publish invalidations. Successful HTTP mutations publish all five datasets (`snapshot`, `tags`, `map`, `namespaces`, `warpDirectory`) after the response succeeds, including when response decoding fails afterward. Failed requests publish nothing. Static mutations reject with `read_only` and publish nothing.

HTTP requests share authentication, permission, throttling and network handling. Statuses 401, 403 and 429 are authoritative. Other errors use the allowlisted `X-Kozane-Error-Code` header or the status fallback. See the [HTTP compatibility mappings](../../../../docs/backend-separation/http-error-compatibility.md). Static reads reject missing records with `not_found` and datasets absent from an export with `unavailable`.

Keepalive is supported only by methods that accept `MutationOptions`. It requests fetch keepalive for a JSON body within the 60 KiB transport budget. It does not guarantee delivery. Reads and other methods below do not accept it.

Hosts can import `PollLifecycle`, `NavigationAdapter`, `NavigationDriver` and `PreferenceStorage` from the public client entry. These adapters keep visibility, wake events, routing and preference storage in the host.

While subscribed, the HTTP backend polls visible workspaces and starts a fresh token baseline for each subscription session. A successful poll after a failure revalidates all datasets even when its token matches the last successful baseline. Hidden or disposed views defer or discard pending work.

Committed writes and workspace-wide external invalidations expire HTTP snapshot validators. The next snapshot request therefore forces server assembly instead of reusing a metadata-only conditional cache entry, including after conservative change tokens. Known unchanged-token filesystem refreshes can retain conditional snapshot reads.

A failed HTTP change-token poll leaves the backend ready and its data version unchanged. The ready state carries an optional `refreshError` until the next successful poll. Shared views show a retry notice and retain their last data. Renewing a subscription retries a failed polling session through the shared throttle deadline. Healthy polling sessions keep their normal timing.

Active file-tree and scope-frame directories share watched listings. Successful snapshot invalidations refresh only displayed directories, including when the database token is unchanged. Failed reads retain existing rows and offer Retry. Closed directories and superseded requests cannot apply late results. Static views retain their embedded listings.

## Dataset reads

No write capability is required. All results are promises of the named type. Namespace metadata uses direct database reads. Snapshot rows share one read transaction. Tags, map and warp-directory aggregation currently use multiple database reads and may include Node enrichment outside a database transaction. Consolidating those read boundaries remains pending in Phase 1. Static reads use embedded data and open no transaction.

## Taskspaces

The optional `taskspaces` API exists only when `capabilities.taskspaces` is true. Node supplies filesystem operations. Static exports with embedded files expose the same interface for reads and reject all writes. LocalBackend does not supply taskspaces.

Paths are relative to the trusted taskspace directory. An empty listing path names its root. Node services validate containment, entry names, file sizes, text encoding and symlinks. File mutations run in a per-taskspace queue, resolving the directory inside the queue. This is filesystem serialization, not a database transaction. Taskspace creation inserts the database record then claims the directory, deleting the record if claiming fails. Rename/removal coordinate database and filesystem changes through Node services rather than one atomic filesystem/database transaction.

Node file errors retain HTTP 400 for invalid paths, 404 for missing entries, 403 for forbidden access, 409 for existing entries or stale signatures, 413 for oversized files and 415 for nontext files. Their backend codes use the HTTP status fallback. Node lifecycle errors retain their existing operation-specific statuses and wording. Static skipped files reject with `limit` for size/budget exclusions and `unavailable` for nontext/unreadable exclusions. A cancelled static file read rejects with `unavailable`.

Every write requires writable capability, publishes all datasets on HTTP success and rejects with `read_only` on StaticBackend. Other than `saveFile`, taskspace methods do not support keepalive.

HTTP validates every taskspace result before returning it. Malformed read results reject with `unavailable` without an invalidation. A successful write with malformed result fields still publishes its committed invalidation, then rejects without replay. Namespace/taskspace identifiers and file signatures retain their declared meanings. `http-taskspaces.test.ts` covers all ten methods, error status preservation, cancellation, keepalive and malformed-result handling. `decoders/taskspaces.test.ts` covers nested metadata, duplicate entries, nullable fields and export truncation reasons.

## Domain mutations

All methods in this section require `capabilities.writable`. HTTP success publishes every dataset through the shared invalidation rule above. StaticBackend rejects every method with `read_only` before looking up identifiers. LocalBackend execution remains pending. Types specify valid caller shapes, while runtime validation also checks numeric finiteness, configured bounds, batch limits and database references.

The table uses `ns`, `card`, `layer`, `partition`, `scope`, `area`, `warp` and `inventory` for required string identifiers. In the endpoint column, paths beginning with `/api` are workspace paths. All other paths are relative to `/:namespaceId/api`. `K` means the declaration accepts `MutationOptions.keepalive`. Methods without `K` do not support it. Bodyless deletes accept the option where declared, but the HTTP transport enables keepalive only when a body exists.

`W` means the entire database mutation runs on one write transaction, owned by the service or the composite database API it calls. Transaction-bound variants reuse their caller's write transaction. `S` means one atomic SQL write without an explicit service transaction. `R+S` means a read followed by a separate SQL write, which is a remaining reference-race audit item in Phase 1. These boundaries describe current implementation.

Names are trimmed, nonblank and bounded, except inventory names, which may be blank. Numeric coordinates are rounded and clamped to the configured canvas. Scope rectangles are also clamped to the minimum frame size and canvas bounds. Batch ID lists require unique nonempty strings, at least one entry and no more than the configured batch limit. Glue creation requires at least two entries. Required fields reject omission and null. Optional fields preserve existing values on update unless the row specifies a different default. Only card width accepts null as a reset value.

Batch refusals retain HTTP 400 with code `validation`, including foreign cards/references, a missing target namespace, full inventories, stored cards in a glue request and unstored cards in a take request. Single-record missing resources generally return 404 with `not_found`. The rows identify exceptions. Existing content, name and batch limits remain 400 validation errors. Driver normalization and remaining direct-write paths stay under Phase 1.

Namespace, layer and partition mutation responses pass runtime decoding before delivery. Creation results require their declared metadata. Rename/reorder acknowledgements require `ok: true`. Removal results require the destination default-row ID, and layer removal also requires complete stacking entries with unique card IDs. Invalid committed results reject with `unavailable` after publishing the committed invalidation, without replay. `http-structure.test.ts` covers each operation. `decoders/structure.test.ts` also checks actual service results and card reassignment during layer and partition removal. Scope and warp mutations also validate results before delivery. Scope rename results must match the scope ID. Area geometry must match its namespace, scope and requested area ID when updating. Warp geometry must match its namespace and requested warp ID when updating. Membership and deletion results require `ok: true`. `http-geometry.test.ts` verifies all eleven operations and rejects mismatched identities after committed invalidation. `decoders/geometry.test.ts` checks actual service geometry clamping, membership and deletion. Inventory mutation responses also pass runtime decoding. Inventory rows must match the destination namespace and requested inventory ID when updating. Released and cleared card IDs must be unique. Placements must target the requested inventory with unique card IDs and integer slots in range. Stow returns changed slots only, including repaired neighbours, so an empty no-op result is valid. Take results must name exactly the dispatched cards and preserve paired-position semantics. Response checks use the prepared request copy rather than mutable caller objects. `http-inventories.test.ts` covers every inventory method, malformed committed results and safe input copying. `decoders/inventories.test.ts` verifies actual service stow/no-op/take/removal behavior and clamping. Card and glue results also pass runtime decoding. Card creation requires a complete new-card row and consistent inventory placements. Updates require stacking plus normalized content when editing text, with conditional refit fields checked together. Squash requires complete unglued pieces in the returned inventory and valid timestamps. HTTP ISO timestamps are decoded to Date values to match the declared service result. Glue results require unique cleared-card IDs. Success acknowledgements and empty stacking or changed-only placement lists retain their operation-specific meanings. `http-cards.test.ts` covers all twelve card/glue operations and prepared-request checks. `decoders/cards.test.ts` checks actual service creation, edits, refits, repeated unglue, stacking and squash wire parity.

## Lifecycle methods

Capabilities, version and state are readonly properties. Captured version stamps remain immutable. Dataset revisions advance only after successful commit or observed external change. HTTP is immediately ready. StaticBackend is ready with a fixed version and no polling. LocalBackend lifecycle transitions remain pending.
